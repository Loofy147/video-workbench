# Delivery Routes, Schedule, and Acceptance Checklists

**Plan date:** 2026-10-15  
**Baseline:** `main` at `4927cfac71f0a5b5a1a59bbfd4bbe39cc6d87fa2`  
**Planning assumption:** One owner/operator, a local-only pilot, and one focused campaign workflow. Dates below are target windows for sequencing work, not externally committed deadlines. Re-estimate if the product scope, team capacity, or deployment target changes.

## Delivery objective

Prove one complete, repeatable company workflow before broadening the product:

> A company operator starts with a real business offering and permitted source material, creates a brief and storyboard, renders a technically validated draft, reviews the claims and rights, and hands off a versioned campaign pack with clear provenance and release status.

Do not treat a passing render, an evidence reference, a green CI run, or a draft ZIP as proof of factual accuracy, rights, reviewer authority, or permission to publish.

## Recommended routes

### Route 1 — Fastest path to a useful result (critical path)

`Real offering and source evidence → brief/storyboard → saved version → watermarked render → owner review → complete draft pack → acceptance record`

Keep this route small. Do not add model providers, remote generation, a database, or multi-user infrastructure unless the acceptance run demonstrates a concrete need.

**Exit criteria**
- [ ] The offering, target audience, objective, differentiators, CTA, and exclusions are grounded in owner-confirmed material.
- [ ] Every factual statement in the brief and storyboard is accounted for in a claim/evidence review.
- [ ] A fresh local run creates a real playable MP4 and a version-scoped pack.
- [ ] An owner/reviewer can identify what is verified, inferred, unverified, or blocked without help.
- [ ] The acceptance record states remaining failures and known limitations.

### Route 2 — Safe media intake (highest-priority product gap)

`Selected file → request limits → extension/content validation → bounded media probe → safe local storage → rights/provenance record → render allowlist → output validation`

Implement in this order: enforce request and file-size limits; validate file signatures/content rather than trusting the browser MIME type; probe media under bounded execution; assign server-generated storage names; prevent path traversal and symlink escapes; hash source bytes; capture origin, rights status, and evidence; only then wire assets into the render path.

Do not allow arbitrary remote URLs, caller-supplied filesystem paths, unbounded probe processes, or automatic publication. Keep uploads local until storage, privacy, retention, and threat-model decisions support a different boundary.

**Exit criteria**
- [ ] Explicit file types, per-file size limits, total request limit, scene count, duration, resolution, and audio limits are documented and enforced server-side.
- [ ] Invalid, truncated, mismatched-extension, malformed, and over-limit files fail with safe structured errors.
- [ ] Probe timeouts/resource limits and subprocess argument handling are tested.
- [ ] Storage names are generated by the server; resolved paths remain inside the project asset root, including symlink/path edge cases.
- [ ] Source hash, detected media properties, origin, rights state, and evidence pointer are preserved into provenance.
- [ ] No upload can bypass technical validation or the fixed draft watermark.

### Route 3 — Claim completeness and evidence review

`Brief + scene text + CTA + captions → candidate factual-claim inventory → evidence/status mapping → reviewer exception list → pack`

Start with deterministic coverage checks and candidate identification, not an assertion that an LLM or heuristic can prove a claim true. Preserve each candidate's source text, location, evidence reference, status, reviewer disposition, and any uncertainty. An automated detector may miss or over-flag claims; reviewers must be able to correct it.

**Exit criteria**
- [ ] Factual claims are identified across all customer-visible copy fields, not only the manually maintained ledger.
- [ ] Every candidate maps to documented source, direct observation, inference, or unverified status.
- [ ] Missing evidence and contradictions are visible as blockers or review items.
- [ ] Source references are not described as verified unless the source was actually inspected and its support recorded.
- [ ] Tests include omissions, duplicate claims, contradictory statements, empty references, and non-factual creative copy.

### Route 4 — Review, approval, and release boundary

`Draft → review requested → changes requested OR approved → release eligibility check → explicitly authorized release`

Technical render success and release approval must stay separate. First decide whether the next real workflow requires only an owner on one local machine or multiple reviewers/remote access. Implement only the matching authority model. Never add a UI-only approval toggle that lets an unverified operator unlock a release.

**Exit criteria before any unwatermarked or publication path**
- [ ] Reviewer identity and authority are bound to a trusted authentication mechanism, not a user-entered name.
- [ ] Review decisions include actor, timestamp, target version/hash, decision, rationale, and prior-state reference.
- [ ] Edit-after-approval invalidates approval for the changed version.
- [ ] Rights, claim-evidence, privacy, brand, and media-technical gates are checked independently.
- [ ] Rejected/changed/stale approvals cannot produce a releasable artifact.
- [ ] The release path has negative tests for missing identity, insufficient authority, stale approval, missing evidence, and rights blockers.
- [ ] If those conditions are not implemented and tested, drafts remain watermarked and the release path remains unavailable.

### Route 5 — Operational readiness and controlled expansion

`Acceptance evidence → threat model → packaging/recovery checks → isolated beta decision → next deliverable chosen by value`

Only after Routes 1–3 pass should we spend effort on remote hosting, durable queues, provider bake-offs, or broad product families. If multiple operators or long-running workloads become real requirements, separately scope authentication/authorization, persistence, backups, retention, queue/cancellation/retry, observability, secrets, deployment isolation, and rollback.

### Scheduling rules

- Keep only **one critical-path feature** in active implementation at a time; let the claim-coverage review run in parallel with asset-intake design only when it does not delay security tests.
- Every window ends with an executable demo, evidence artifact, or explicit blocker—not just a document update.
- If an acceptance gate fails, move the dependent work; do not preserve the dates by removing the gate.
- Re-estimate every window after its first working session and after a material scope change.
- Provider/model evaluation is deferred until a representative workload shows the deterministic renderer is insufficient.

## Working cadence

1. **Start of cycle:** Choose one measurable outcome; confirm dependencies and input materials; write or update the issue acceptance checklist.
2. **Each work session:** Make the smallest testable change. Record command/test output and mark blockers while context is fresh.
3. **Mid-cycle check:** Exercise the happy path and at least one failure path; adjust scope before adding adjacent work.
4. **End of cycle:** Demonstrate the workflow from a clean start; attach logs/reports/screenshots or artifact checksums where appropriate; record open defects and the next gate.
5. **Release decision:** Owner reviews business accuracy and usefulness; engineering review confirms tests and security boundaries; rights/release approval remains a separate explicit decision.

## Reusable checklists

### Before starting an issue
- [ ] User problem and intended outcome are stated in one or two sentences.
- [ ] Scope and explicit non-goals are listed.
- [ ] Dependencies and affected contracts/files are identified.
- [ ] Acceptance tests cover success, invalid input, and failure/recovery where relevant.
- [ ] Evidence needed to prove completion is named.
- [ ] The task can be reviewed and merged independently.

### Pull request readiness
- [ ] Change is the smallest complete unit; no unrelated refactor is bundled.
- [ ] Tests added or updated for changed behavior and failure modes.
- [ ] Full repository suite passes: `python -m unittest discover --start-directory tests --pattern "test_*.py" --verbose`.
- [ ] CI is green on the exact PR head.
- [ ] Docs and known limitations match actual behavior.
- [ ] Secrets, user media, generated video, private data, and unreviewed third-party content are absent.
- [ ] Paths, subprocess calls, file limits, HTML/text handling, and permissions are reviewed where applicable.
- [ ] Evidence supports every claim that the change works; no manual checks are described as automated tests.

### Campaign-pack acceptance
- [ ] Real offering and audience confirmed by the owner.
- [ ] Source inventory records location, date/revision, allowed use, rights state, and reviewer notes.
- [ ] Brief and every scene/caption/CTA reviewed for factual claims.
- [ ] Creative copy is distinguishable from factual claims and inferences.
- [ ] Assets have permitted use and safe provenance; no unknown-rights asset is represented as cleared.
- [ ] Saved version renders to a playable MP4; codec, resolution, frame rate, duration, and audio match the contract.
- [ ] Sidecar checksum matches the delivered artifact; pack contains the same-version brief, manifest, render, and provenance.
- [ ] Draft watermark and `NOT FOR PUBLICATION` status are present while approval is absent.
- [ ] A reviewer can inspect the pack without relying on undocumented tribal knowledge.
- [ ] Acceptance result, rejected items, and unresolved risks are recorded.

### Before any beta or release
- [ ] Deployment boundary and intended users are stated; no accidental LAN/tunnel exposure.
- [ ] Authentication, authorization, reviewer authority, and audit trail are tested if multi-user access is enabled.
- [ ] Data minimization, storage location, retention, deletion, backup, and recovery have documented owners.
- [ ] Secrets are stored outside source control and logs redact sensitive values.
- [ ] Upload/probe/render limits and failure behavior resist malformed or resource-exhausting input.
- [ ] Release decisions bind to the exact project version and artifact checksum.
- [ ] Rights, factual claims, privacy, brand, accessibility, and technical quality receive separate review.
- [ ] Rollback/disable procedure and known limitations are documented.
- [ ] Any unresolved critical risk blocks the release and is visible to the owner.

## Decision log and status reporting

Maintain each cycle's outcome in GitHub issues/PRs. At minimum, report: **completed**, **evidence**, **blocked by**, **risk/unknown**, and **next gate**. Label estimates as estimates and distinguish observed behavior, simulation, inference, and unverified claims. Do not describe this plan as a commitment or the product as beta-ready merely because these dates are written down.
