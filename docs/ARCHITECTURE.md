# Architecture — Initial Boundaries

**Status:** The first browser interface and file-backed project store are implemented as a local-only pilot. No deployed multi-user topology, remote access model, or production identity system has been selected.

## Architectural intent

Keep product contracts provider-independent. The workflow should be usable without downloading model weights, requiring a GPU, or binding business state to a single vendor. External systems belong behind explicit adapters. This is an internal-company workbench first, with a first vertical slice from business offering to video campaign pack.

## Current components

1. **Product interface** — a responsive browser UI in web/ for editing a campaign brief and card storyboard, browsing saved projects, rendering a draft, and inspecting/download artifacts. The UI uses local JavaScript, CSS, and HTML without a front-end framework or external asset fetches.
2. **Application orchestration** — tools/workbench_server.py serves the UI and a small same-origin JSON API. It validates and normalizes user input, saves versioned project documents, invokes the renderer, and records success/failure state.
3. **Domain contracts** — campaign manifests use schema_version 1. Each project has a stable random identifier, saved versions, a Markdown brief, a JSON render manifest, and separate render/approval outcomes. Manifest IDs and paths are generated by the server rather than accepted from browser input.
4. **Execution adapter** — src/video_workbench/render.py uses an installed FFmpeg executable to assemble cards, images, video, and optional audio; FFprobe validates output. Generative backends remain optional and are not part of this UI slice.
5. **Artifact and provenance layer** — the renderer's JSON sidecar links the manifest hash, source hashes/provenance, renderer/tool versions, output checksum and size, media properties, technical validation, claim evidence, approval assertions, and release blockers.
6. **Persistence** — the first UI writes project metadata, immutable versioned Markdown briefs, JSON manifests, rendered MP4s, and sidecars beneath the Git-ignored .workbench/projects/ directory. This is local file persistence, not a database, queue, backup, or team store.
7. **Observability** — render state and actionable errors are retained in the project record. Structured production logs, correlation IDs, metrics, cancellation, durable job queues, and attempt history are still future work.

These are logical responsibilities, not a mandate to deploy separate services. The current implementation deliberately uses the standard library and a single local server to reduce setup cost.

## Current project lifecycle

Plan editing creates a new project version. A saved version moves from draft to rendering and then to rendered_draft or render_failed. A rendered version is not overwritten; saving edits creates a new version and a new output path. Technical render status remains separate from publication approval.

The current UI renders watermarked preview drafts only. The manifest's approval status remains draft, and the renderer records publication blockers. The UI does not expose unwatermarked output or allow an operator to self-assert identity-bound approval.

## Contract principles

- Keep project/version identifiers stable and generated by the system.
- Record the input manifest, renderer and tool versions, timestamps, output validation, checksum, and result metadata.
- Preserve prior versioned manifests and brief content; do not silently replace the evidence for an earlier render.
- Make assumptions and unverified claims visible; do not invent factual company claims.
- Keep user-entered content out of request logs and escape/render it as text rather than executable HTML.
- Constrain browser input to short card scenes and generated relative output paths. The browser cannot submit arbitrary filesystem paths or upload local assets.
- Represent output as artifact references/metadata, not as MP4 bytes in project JSON.
- Treat technical success, factual accuracy, media rights, reviewer authority, and permission to publish as separate concerns.

## Local-only security boundary

The server binds to 127.0.0.1 and validates the Host header and the Origin on mutating requests. It applies a restrictive Content Security Policy, caps JSON request size and storyboard length/duration, and uses a fixed draft watermark. This is a deliberate local-pilot boundary, not a production security guarantee.

There is no authentication, authorization, database, encryption-at-rest guarantee, remote sharing, tenant isolation, backup, or automated retention. Do not expose the listener through a tunnel, reverse proxy, or LAN port. Before multi-user or remote use, complete threat modeling, identity-bound approval, permissions, secret handling, storage/retention, observability, and operational recovery.

## Initial execution choice

Deterministic media assembly is the first video path. It works with an installed FFmpeg executable and does not require GPU resources, model weights, or remote-generation credentials. The application should validate the resulting file and report failure explicitly. Do not bundle FFmpeg until the exact build/distribution and license obligations have been reviewed.

If a model-based generator is adopted later, it must sit behind a product-owned contract and be evaluated independently for cost, quality, runtime, terms, output provenance, security, cancellation, and failure behavior.

## Current limits and next selection gates

The current UI supports business brief fields, card storyboard editing, versioned saves, a watermarked MP4 render, and artifact/provenance download. It does not support asset uploads, structured claim/evidence editing, authenticated approvals, team collaboration, job queues, cancellation/retry, database persistence, deployment, or a live ContribQuest walkthrough.

Choose a database and queue only when real concurrent workloads, multi-user permissions, or recovery requirements justify them. Add asset uploads only with safe storage paths, media probing, upload limits, provenance capture, and rights policy. No model/provider benchmark is needed until a representative workload shows that deterministic cards and approved footage are insufficient.
